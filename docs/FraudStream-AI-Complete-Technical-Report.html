1Executive summary

FraudStream AI is a complete fraud detection system, built from an empty folder to a running three-tier application. It ingests historical card transaction data, trains and compares four detection models, replays unseen transactions as a live event stream, scores each one in under a millisecond, escalates risky accounts, explains individual decisions, and lets a human analyst work each case to a documented outcome.

The single most important number
p95 inference latency is 1.588 ms against a 50 ms requirement, which is roughly 31 times inside budget. That headroom is not an accident: latency is a hard gate in model selection, and the winning model was chosen partly because a more accurate competitor was too slow. Section 8 shows exactly how that trade-off was made and section 17 shows where the milliseconds go.

What makes this more than a classifier notebook

  • It streams. The processing loop handles one transaction at a time through a real Python generator, so the architecture matches how payment authorisation actually works rather than scoring a CSV in bulk.
  • It is honest about imbalance. Accuracy is never reported anywhere in the codebase. With 0.1667 % fraud, a model that predicts "legitimate" every time scores 99.83 % accuracy and catches nothing.
  • It tunes the decision, not just the model. The threshold is 0.184152, chosen by maximising F2 subject to a precision floor of 0.50, rather than being left at the default 0.5.
  • It explains itself. Every alert carries additive TreeSHAP contributions in log-odds space plus human-readable reason codes, so an analyst sees why the model fired.
  • It closes the loop. Analysts assign, annotate, transition and resolve cases with optimistic concurrency control, and the resolution codes become measurable feedback.
  • It is verified. 60 automated tests, an end-to-end smoke harness with 23 assertions, and a browser harness that drives real interactions.

2Problem statement and objectives

2.1 The business problem

Card fraud has to be stopped while the transaction is still in flight. Once an authorisation is approved, the money has moved and the institution is into chargeback and recovery, which is slower and more expensive than prevention. That creates three constraints that pull against each other:

ConstraintWhy it is hardHow this project answers it
Speed A scoring decision sits inside the payment authorisation path. Tens of milliseconds of extra latency degrades checkout conversion. Hard latency requirement of 50 ms, measured through the real serving path, enforced as a gate during model selection. Achieved p95 of 1.588 ms.
Rarity Fraud is 0.1667 % of transactions. Standard accuracy and default thresholds are actively misleading at that ratio. PR-AUC as the selection metric, class reweighting inside every model, and a tuned threshold with an explicit precision floor.
Trust A score alone is not actionable. An analyst must know why a transaction was flagged, and a blocked customer deserves a reason. TreeSHAP feature contributions plus behavioural reason codes on every alert, presented in an investigation workbench with an audit trail.

2.2 Why "pseudo-streaming"

A production system would consume a message broker such as Kafka. We do not have a live card payment feed, and inventing one would prove nothing. Instead we take the final 15 % of a real dataset's timeline, which the model has never seen, and replay it in original chronological order through a Python generator, one transaction per iteration, with a configurable inter-arrival delay.

Why this is the right simplification
The property that matters for the architecture is one-record-at-a-time processing with bounded memory and a clean stop. A generator gives exactly that. Swapping the generator for a Kafka consumer changes the source of the loop, not the loop itself, because everything downstream already assumes single-event handling. The dataset order is never shuffled, so no future transaction can influence a past decision.

3.2 Decisions that shaped everything after them

DecisionAlternative we rejectedConsequence
One central config module Constants defined near where they are used Feature order, risk bands and the latency target exist in exactly one place, so the training path and the serving path cannot silently diverge.
Chronological split Random train_test_split No future information leaks backwards. It also makes the test split usable as a realistic replay stream, which the whole streaming demo depends on.
Generator, not DataFrame pandas.read_csv then iterate rows Bounded memory, honest per-transaction latency, and a clean mid-file stop. A test proves laziness by counting parse calls.
Latency as a selection gate Pick the highest PR-AUC model Random Forest scored higher (0.8715 vs 0.8472) but needed 33.16 ms at p95. XGBoost ships instead at 1.76 ms, keeping 96 % of the budget free.
Two feature code paths Reuse the vectorised path for single records Allocating a DataFrame per transaction would waste most of the latency budget. A parity test keeps the scalar and vectorised paths numerically identical.
Background persistence writer Write to the database inline Network round trips never count against the 50 ms budget. The queue sheds load rather than blocking the stream.
Derived identity, never a feature Feed account and merchant into the model The dataset is anonymised, so account identity is a deterministic hash. Using it as a feature would be circular. A test asserts none of these keys appear in the model feature list.
In-memory rolling state Query Postgres for every dashboard refresh The dashboard works with no database configured, and /api/metrics never runs an aggregate query on the hot path.
The through-line
Every one of those decisions trades a small amount of convenience for a property that can be demonstrated: bounded memory, measurable latency, no leakage, or no drift between two code paths. That is why the test suite is able to assert architectural properties and not just output values.

5System architecture

5.1 The three tiers

5.2 The three threads inside the engine

Concurrency here is deliberate and small. Three kinds of thread exist, each with one job, and the boundaries between them are the reason the latency budget holds.

ThreadCreated byResponsibilityProtection
Request threads Uvicorn Serve HTTP. Read rolling state, control the stream, mutate investigation cases. Every read takes a detached snapshot, so a request never holds a lock while serialising JSON.
pseudo-stream StreamProcessor.start Owns the scoring loop. Pulls events from the generator, predicts, assesses risk, updates accounts, raises alerts, opens cases. A single threading.Lock prevents two concurrent streams; a threading.Event requests a cooperative stop.
supabase-writer SupabaseWriter Drains a 10,000-slot queue, groups rows by table, and flushes in batches of 25 or every second. Producer/consumer queue with a sentinel shutdown. If the queue fills, rows are dropped with a warning rather than blocking the scoring loop.
The consequence a reviewer should know
Because the stream runs as an in-process background thread, the engine must be deployed with a single worker process. Two workers would each hold their own independent stream state and rolling buffers, and the dashboard would see whichever worker answered the request. This is documented in the deployment guide, and section 22 explains what a multi-worker design would require.

6End-to-end data flow

6.1 The life of one transaction

This is the sequence that runs for every single record. Steps 2 to 4 are the timed section that the 50 ms budget applies to; everything after step 7 happens off the critical path.

The eleven steps, in execution order
#StepWhat happensImplementation detail
1 Receive and validate The generator reads one CSV row, checks that Time and Amount exist, are numeric and non-negative, and that all 28 PCA components parse. A malformed row raises an internal error that is caught, counted and skipped. The stream continues; it never dies on bad input.
2 Build the feature vector 28 PCA components are copied into a pre-allocated array, then five engineered values are appended: amount, log amount, seconds of day, hour of day and a night flag. A NumPy array of exactly 33 float64 values in fixed order. No DataFrame is created.
3 Transform Median imputation then z-score standardisation, using statistics fitted on the training split only. The same serialised scikit-learn Pipeline object that training produced, so offline and online transforms cannot drift.
4 Predict XGBoost forward pass returns the probability of the positive class. This is where the timer stops. Measured average 0.9739 ms.
5 Risk assessment The probability is rescaled so the tuned threshold lands exactly on 0.70, then mapped to a band and an action. Piecewise linear and monotonic, so relative ordering of transactions is preserved.
6 Behavioural features Seven behavioural values are computed from the account's prior activity: prior count, average amount, deviation, seconds since previous, one-hour velocity, distinct recent locations, high-value flag. Computed before the account profile is updated, so the current transaction can never be part of its own baseline.
7 Account update The profile absorbs the new transaction, recomputes seven weighted signals and reassigns an account risk level. Welford update for mean and variance; bounded deques for recent times and locations.
8 Alert decision If the risk score is at or above 0.70, an alert row is created with a UUID, an alert type and an open status. Alert type is the first matching rule of six; reason codes capture all matching evidence.
9 Explain and open a case For alerting events only, TreeSHAP contributions are computed and an investigation case is opened linking alert, transaction snapshot, explanation and reason codes. Deliberately after the latency measurement, so explainability costs nothing on the measured path. Non-XGBoost models degrade to an explicit "unavailable" result.
10 Record in rolling state Counters, risk histogram, latency window, transaction and alert ring buffers, per-second timeline bucket and the live confusion matrix all update under one lock. Only transactions carrying a ground-truth label update the confusion matrix.
11 Hand off persistence Rows are enqueued for the writer thread. Account rows are only sent when the account carries risk, to keep write volume sane. Fire and forget. If Supabase is not configured, this is a no-op and the dashboard runs from memory.

6.2 How the dashboard stays current

Two independent mechanisms feed the console, which is why it still works when the database is not configured.

Mechanism 1: polling the engine
A single interval in StreamContext fetches six endpoints per tick. The cadence is adaptive: no timer at all while the first load is in flight, 2000 ms while a stream is running, and 8000 ms when idle. Pausing the feed skips the tick without destroying the timer. This path needs only the API.
Mechanism 2: Realtime push
One websocket channel, fraudstream-live, subscribes to five table events: transaction inserts, alert inserts, any account risk change, any investigation case change and note inserts. Rows are merged by primary key, so a row that arrives by both push and poll can never appear twice. Requires Supabase.

Why the duplicates matter

8.2 Threshold tuning: why the cut-off is 0.184152, not 0.5

A default threshold of 0.5 assumes both errors cost the same and both classes are equally common. Neither is true here. A missed fraud costs the transaction value; a false alarm costs a review. Our tuning procedure runs on the validation split only:

  1. Sweep the entire precision-recall curve.
  2. Discard every threshold where precision falls below 0.50, so at least half of all alerts must be real.
  3. Among those that survive, maximise F2, which weights recall four times more heavily than precision.
  4. Clamp the result strictly inside (0, 1), because a threshold of exactly 1.0 would only fire on a probability that is bit-for-bit 1.0.

8.5 Why validation scores exceed test scores

F1 falls from 0.8491 to 0.7500 between validation and test. We are not hiding that, and there is a straightforward explanation:

  • The threshold was tuned on validation. Any threshold chosen to optimise a split will flatter that split. Test is the only untouched measurement, so 0.75 is the number we stand behind.
  • Tiny positive counts. Test contains 52 frauds. Moving three transactions across the boundary shifts recall by nearly six percentage points. Confidence intervals at this sample size are wide, and section 22 states that plainly.
  • Time moves forward. Test is the latest window in the timeline. A drop from validation to test is the expected signature of mild distribution drift, which is exactly what a chronological split is designed to expose rather than hide.

9Risk engine mathematics

A raw probability is a poor operational signal: 0.184152 means "flag this" for our model, but that number is meaningless to an analyst and would change on retraining. The risk engine converts probability into a stable, human-readable 0 to 1 risk score with fixed action bands.

9.1 Probability to risk score

# Piecewise linear, monotonic, anchored on the tuned threshold
if probability <= threshold:
    score = 0.70 * (probability / threshold)
else:
    score = 0.70 + (1.0 - 0.70) * ((probability - threshold) / (1.0 - threshold))
PropertyConsequence
probability 0 maps to 0.00Clean transactions sit at the bottom of the scale.
probability = threshold maps to exactly 0.70The alert boundary is a fixed constant, 0.70, no matter what the model's threshold becomes after retraining.
probability 1 maps to 1.00The scale is fully used.
Strictly monotonicThe relative ordering of transactions by risk is never altered, so no ranking information is lost in the conversion. A 101-step sweep test asserts this.

The suspicion floor
After the weighted sum, one override applies: if an account has produced at least one suspicious transaction, its risk score is floored at 0.70. Without it, an account with 400 clean transactions and one confirmed critical hit would average down into the low band and vanish from the queue. 9.4 Behavioural features are computed before the update

Ordering matters here and is easy to get wrong. For each transaction the engine first reads the account's prior state to build behavioural features, and only then folds the new transaction into the profile. If the order were reversed, the transaction would appear in its own baseline, its amount deviation would be biased towards zero, and its velocity count would always be at least one. A dedicated test asserts prior-activity-only behaviour, and the transaction detail drawer tells the analyst the same thing.

The detail that shows real security thinking
Row level security can restrict which rows a user touches, but not which columns. An analyst needs to change an alert's status, and must never be able to change its risk score. So the migration revokes update on the whole alerts table and re-grants update on the status column alone. A compromised browser token can move an alert to "dismissed"; it cannot rewrite the score that raised it. The investigation tables go further and are read-only for the browser. All case mutations must pass through the API, which verifies identity, validates transitions, applies the version check and records who did what. Granting direct table writes would have bypassed all four of those guarantees.

12.3 Realtime configuration

Five tables are published for live replication: transactions, alerts, account risk, investigation cases and investigation notes. Each is set to full replica identity so update events carry the complete row rather than only changed keys. The publication is created only if absent and each table is checked before being added, which is what makes the migration re-runnable. Realtime respects row level security, so a subscriber receives only rows it would have been allowed to select.

15Advanced feature: the explainable investigation workbench

This is the newest and most substantial addition, and the one that turns a detector into a tool an analyst can actually work with. It spans all four layers: model explainability, backend state, database schema and a full user interface.

15.1 The problem it solves

Before this feature the system could tell an analyst that transaction TXN-0001326 scored 0.999993 and was critical. It could not tell them why, could not record what the analyst decided, and could not measure whether the model's alerts were actually correct. Three consequences followed: no auditability, no coordination between analysts, and no feedback signal for the next training round.

15.2 Layer one: explainability with native TreeSHAP

AspectImplementation
MethodXGBoost's built-in contribution prediction, which returns exact additive TreeSHAP values plus a bias term.
Output spaceRaw margin, that is log-odds. Contributions sum with the base value to reproduce the margin, and the sigmoid of that margin reproduces the probability. The report states this explicitly so nobody misreads a contribution as a probability delta.
Verification built inThe payload carries both the model probability and the probability reconstructed from the contributions. On the verified live case both read 0.999982, which proves the explanation corresponds to the actual decision.
Cost controlExplanations are computed only for alerting events, and deliberately after the latency measurement, so the 50 ms budget is untouched. Non-alerting traffic pays nothing.
RankingFeatures are sorted by absolute contribution and truncated to the top eight, each labelled as raising or reducing risk, with the observed feature value shown alongside.
Graceful degradationAny non-tree estimator, or any failure inside the call, returns an explicit unavailable result with a reason string. The case still opens with reason codes, and the interface shows an "Unavailable" badge instead of an empty panel.

Alongside the mathematical explanation, every case carries the behavioural reason codes from section 9.5. The two answer different questions: TreeSHAP answers "which model inputs moved this score", reason codes answer "what about this behaviour is unusual". An analyst needs both.

15.3 Layer two: case lifecycle with optimistic concurrency

CapabilityBehaviour
Automatic creationEvery alert opens a case with a readable number, a priority derived from the risk band, an immutable transaction and alert snapshot, the explanation, the reason codes and a seeded creation event.
Duplicate suppressionIf a still-open case exists for the same transaction, it is reused rather than duplicated. This matters because restarting a stream without a reset replays rows that were already scored.
AssignmentOwnership can be claimed or released, recording who assigned whom and when.
NotesAppend-only, length-limited, attributed, and never editable, so the trail cannot be quietly rewritten.
Status transitionsOpen, investigating, resolved or dismissed, mirrored onto the underlying alert so the triage queue and the workbench cannot disagree.
ResolutionSix outcome codes, a written rationale and an optional analyst confidence value. A duplicate resolution dismisses the case rather than resolving it.
Audit trailEvery mutation appends an event with actor, timestamp and a human-readable description.
Analyst bias guardThe dataset's ground-truth label is stripped from the case snapshot. An analyst must judge the evidence, not read the answer.
Bounded memoryCases beyond a 2,000-case ceiling are evicted oldest-first, and both lookup indexes are cleaned with them.
Why optimistic concurrency rather than locking
Two analysts can open the same case. If both submitted a status change, a last-write-wins design would silently discard one decision. Instead every case carries a version that increments on every mutation, and every write includes the version the analyst was looking at. A mismatch returns 409 Conflict with a message telling them to refresh. This is the same technique databases use for row versioning, applied across HTTP requests, and it holds no lock while a human thinks.

15.4 Layer three: API and persistence

Seven endpoints were added, all additive, so no existing response shape or latency characteristic changed: list cases, workflow metrics, case detail, assignment, notes, status and resolution. Two tables were added in a separate migration, both read-only for the browser, with write access reserved for the engine's service role. Cases are upserted on their identifier so a repeated flush is harmless, and notes are inserted append-only.

16.2 Defence layers

LayerControl
Transport surfaceCORS restricted to four explicit development origins, methods limited to GET, POST, PATCH and OPTIONS, and only three request headers allowed. No PUT or DELETE exists anywhere.
IdentityEvery route except health requires a bearer token, verified against the auth provider with a 60-second bounded cache.
Input validationDeclarative schemas enforce numeric ranges, regex-constrained statuses, string length caps and unknown-field rejection before any handler runs.

Database rowsRow level security on all seven tables. The anonymous role reaches nothing. A user sees only their own profile row.

16.3 Known weaknesses, stated plainly

WeaknessImpactRecommended fix
Authentication fails open If the require-auth flag is set but either Supabase value is missing, every protected route accepts requests as a development user with only a log warning. A misconfigured deployment would be publicly writable. Refuse to start when authentication is required but unverifiable, so the failure is loud at boot rather than silent at runtime.
No role authorisation The profile role column exists with four values, but no endpoint checks it. Any authenticated user can start a stream, upload a dataset or resolve a case. Add a role requirement to the auth dependency and restrict stream control and upload to admin or developer roles.
Users can edit their own role The profile update policy covers the whole row, so a user could set their own role to admin. Harmless today because roles are unenforced, but it becomes an escalation path the moment they are enforced. Revoke update on the role column, mirroring the alert status pattern already used.
Demo mode bypasses sign-in A build flag allows entering the console with no credentials. Defaults to off and is documented as local-only. Keep it out of deployed builds; the code comment says so and the login screen warns on screen.
In-memory state is not durable Restarting the engine clears rolling buffers and open cases. Rows already written to the database survive. Rehydrate cases from the database at startup; noted in the roadmap.
Why we list these rather than omit them
Each item is a deliberate development-time convenience with a known production fix, not an oversight we discovered while writing this report. A reviewer who finds an undisclosed fail-open auth path will discount everything else in the document; a reviewer who sees it disclosed with a one-line remedy reads it as engineering maturity.

17.3 Memory behaviour

Memory is bounded by construction, not by hope. Every buffer has a hard maximum, so a stream can run indefinitely without growth: 5,000 latency samples, 500 transactions, 500 alerts, 120 timeline buckets, 64 recent events and locations per account, 2,000 investigation cases and a 10,000-row write queue. The generator holds one row at a time, and the training pipeline explicitly releases intermediate frames between stages.

What we measured versus what we did not
Latency and throughput are measured on a single development machine with the stream running as fast as the file can be read, reaching roughly 312 transactions per second in a verified run with zero inter-arrival delay. We have not load-tested concurrent API clients, and we have not measured behaviour under a real broker. Section 22 lists both as open work rather than implying they are done.

19Engineering rigour: a bug we found and fixed

While verifying the workbench we found a real defect. It is included here deliberately, because how a team finds and fixes a bug says more than a list of features.

Symptom
The investigations page listed seven active cases while the alerts page was empty. Cases were being shown for fraud that no longer existed in the system.
Diagnosis
Live inspection confirmed the divergence exactly: 0 alerts in the buffer, 7 cases, and all seven case transaction identifiers had no matching alert.

19.1 Root cause

Starting a stream with the reset option clears three things: the transaction feed, the alert buffer and account risk. When the investigation store was added, it was never included in that reset. So cases outlived the run that created them, and their alert links dangled. A second defect shared the same origin: replaying the same rows without a reset opened a duplicate case for a transaction that already had one.

19.2 The fix

ChangeDetail
Reset method on the case storeClears cases and both lookup indexes under its lock, with a comment explaining that database rows are the durable history and are deliberately left alone.
Wired into the stream lifecycleA resetting stream now clears cases alongside the alerts they belong to.
Duplicate guardIf a case for the same transaction is still open or investigating, it is reused. Closed cases still allow a genuinely new investigation.

The transferable lesson
The bug was not in the new feature's logic; the case store worked correctly in isolation. It was in the lifecycle contract between an existing subsystem and a new one. When a system has several stores that must be cleared together, "reset" is a cross-cutting concern, and adding a store means joining that contract. That is exactly the class of defect that unit tests on the new component alone will never catch, and it is why we verified the feature against a running system rather than only against its own tests.

21.1 Machine learning

TermMeaning in this project

Ring bufferA fixed-capacity queue that overwrites its oldest entry when full. Keeps dashboard memory constant no matter how long a stream runs.
ThreadAn independent line of execution inside one process. We use three kinds: request handlers, the scoring loop, and the database writer.
Lock and re-entrant lockMechanisms ensuring one thread at a time touches shared state. Re-entrant means the same thread may acquire it again, which we need because internal helpers call each other.
Producer and consumer queueOne thread enqueues work, another drains it. Decouples scoring speed from database speed.
Back-pressure and load sheddingWhen a queue fills, you either slow the producer or drop work. We drop and count, because pausing fraud scoring to wait for a database write would be the wrong trade.
Optimistic concurrencyInstead of locking a record while a human decides, you attach a version number and reject a write that was based on stale data. Produces our 409 responses.
IdempotentSafe to run more than once with the same result. Our migrations and our case upserts are idempotent.
Singleton with double-checked lockingCreating an expensive object exactly once per process without paying lock cost on every subsequent access. Used for the model, the processor and the writer.
Welford's algorithmComputing a running mean and variance in one pass with constant memory and better numerical stability than summing squares.
Percentile, p95 and p99The value below which that share of samples falls. We report p95 and p99 latency rather than only the average, because tail behaviour is what users feel.
Row level securityDatabase rules deciding which rows a role may see or change, enforced by the database itself rather than by application code.
Column-level grantPermission to modify specific columns only. How we let analysts change an alert's status but never its score.
JWT bearer tokenA signed, short-lived credential sent with each request in the authorisation header, verified server-side.
Path traversalAn attack that uses .. or absolute paths to reach files outside the intended directory. Blocked by a validator and asserted by six tests.
CORSBrowser rules governing which origins may call an API. Ours allows four explicit development origins and four methods.
Realtime replicationThe database streaming its changes to subscribers, so the dashboard updates on write instead of waiting for the next poll.
Code splitting and lazy loadingDeferring download of code until it is needed. The console chunk is not fetched by visitors to the landing page.
Optimistic UI updateShowing the expected result immediately and reconciling with the server afterwards, so the interface feels instant.
Context providerA React mechanism for sharing state with a whole subtree without passing props through every level. One provider holds all live data.
Fail open and fail closedWhat a system does when a security check cannot run. Ours currently fails open for authentication, which section 16 flags with the fix.

22Limitations and roadmap

22.1 Honest limitations

LimitationWhy it existsWhat it means for the results
Two days of 2013 data The public dataset covers a 48-hour window from one European card issuer. Nothing here proves seasonal or regional generalisation. Fraud patterns have also moved on since 2013.
Only 52 frauds in the test split Chronological splitting of a rare event leaves few positives in the final window. Confidence intervals are wide. Three transactions crossing the boundary move recall by about six points, which is why validation and test F1 differ by 0.10.
Anonymised features The publishers replaced original fields with PCA components. An explanation can say V14 pushed the score up, but not what V14 represents in business terms. With real fields the same TreeSHAP output would name a merchant category or a device.
Threshold is dataset-specific 0.184152 was tuned on this validation split. It must be re-tuned for any other data source or cost structure. It is stored in metadata, not hard-coded, precisely so it can move.
Synthetic account attributes The dataset has no account, merchant or location fields. Account-level aggregation demonstrates the mechanism correctly, but the groupings are hash-derived, not real customer relationships.
No drift monitoring Out of scope for this iteration. Nothing detects the model degrading over time. The live confusion matrix is the closest available signal.
Single-process state Rolling buffers and cases live in memory. The engine must run one worker, and a restart clears open cases although persisted rows survive.
Not load tested We measured single-transaction latency and single-client throughput only. Behaviour under many concurrent dashboard clients is unmeasured, and we do not claim it.
Documentation drift One README still cites an older test count of 53 while the suite now has 60. Cosmetic, and disclosed here rather than left for a reviewer to find.

PriorityIncrementRationale and approach
1Fail closed on authentication, and enforce rolesRefuse startup when auth is required but unverifiable; add a role requirement to the dependency; revoke update on the profile role column. Small change, removes the largest disclosed risk.

23Panel question preparation

The questions most likely to be asked, with answers grounded in evidence from this project.

What is your F1 score and your accuracy?
On the held-out test split, F1 is 0.75 with precision and recall both exactly 0.75, and accuracy is 99.94 %. On validation, F1 is 0.8491 and accuracy is 99.96 %. We lead with F1 because accuracy is nearly uninformative here: predicting "legitimate" for every transaction scores 99.88 % on the same split while catching zero fraud. Our balanced accuracy is 87.48 % and our Matthews correlation is 0.7497, which are the figures that actually separate our model from that constant function.
Why is your accuracy so high but your F1 comparatively modest?
Because 42,508 of 42,560 test transactions are legitimate and we classify almost all of them correctly, which dominates accuracy. F1 looks only at the 52 frauds and the 52 alerts: we caught 39, missed 13 and raised 13 false alarms. That is the number that reflects the actual job.
Why did you not choose the model with the best score?
Random Forest scored PR-AUC 0.8715 against XGBoost's 0.8472, so on quality alone it wins. Its p95 latency was 33.16 ms out of a 50 ms budget, on an idle laptop, leaving nothing for a loaded production host. We apply a hard gate at 50 ms and a comfort filter at 25 ms, then take the best PR-AUC among survivors. We traded 0.024 PR-AUC for a 19-fold latency improvement, and the training run logs that decision explicitly.
How do you know there is no data leakage?
Four independent controls. The split is chronological, so training data always precedes test data. Duplicates are removed before splitting, so a row cannot appear on both sides. The imputer and scaler are fitted on the training split only. And an explicit check refuses any feature whose name resembles a label, recorded as passed in the model metadata. The derived account and merchant attributes are also excluded from the feature list, with a test asserting it.
Is this real streaming, or are you replaying a file?
It is a replay, and we call it pseudo-streaming rather than dressing it up. What matters architecturally is that processing is one record at a time with bounded memory and a clean stop, which a Python generator gives us and a test proves by counting parse calls. Replacing the generator with a broker consumer changes the source of the loop, not the loop, because everything downstream already handles single events.
How would this scale to production volumes?
Inference has roughly 98 % of its budget unused, so per-transaction cost is not the constraint. Three things would change: swap the generator for a broker consumer with consumer groups, move rolling state into Redis so multiple workers stay consistent, and run the scoring loop as its own process. The persistence layer already batches and sheds load, so it is the part least likely to need redesign. We have not load tested concurrent clients, and we do not claim a throughput figure we have not measured.
What happens when the model is wrong?
Both directions are handled. A false positive becomes a case an analyst can resolve as a model false positive, which is recorded as feedback. A false negative shows up in the live confusion matrix whenever the replayed data carries a label. Neither is silent. The resolution codes are the beginning of the retraining loop described in the roadmap.
Can you explain a specific decision to a customer or a regulator?
Yes, at two levels. TreeSHAP gives exact additive contributions per feature, and we verify fidelity by reconstructing the probability from those contributions: on a verified live case both the model probability and the reconstruction read 0.999982. Reason codes then translate the behaviour into words with the observed value and the threshold crossed. The honest limitation is that the dataset's features are anonymised components, so we can say V14 drove the score but not what V14 means in business terms.
What is the weakest part of this project?
Authentication currently fails open: if the auth flag is set but a Supabase key is missing, every protected route accepts requests as a development user with a single log warning. It is convenient locally and dangerous in a deployment. The fix is to refuse startup in that state, and it is the top item on our roadmap. The second weakest point is statistical: 52 test frauds is a small sample, so our metrics carry wide confidence intervals.
What did you learn that you did not expect?
That the most valuable bug was in a contract, not in an algorithm. Our case store passed its own tests, but it had not joined the lifecycle contract that clears state on a stream reset, so the workbench showed cases for alerts that no longer existed. Component-level tests could not catch it. That is why we verify features against a running system, and it is documented in section 19 rather than quietly fixed.
How much of this is your own work rather than a library?
The libraries provide the estimators, the HTTP framework and the chart primitives. What we built is roughly 14,100 lines across 97 source files: the risk mapping and account aggregation mathematics, the streaming loop and its concurrency model, the latency-gated selection rule, the explanation and case workflow layers, the database security model, the whole interface, and the verification harnesses.

Closing statement

FraudStream AI began as a requirements document and a CSV file. It now trains and compares four models on 283,726 real transactions, ships the one that satisfies both a quality and a latency requirement, scores unseen transactions in under a millisecond, escalates accounts on seven weighted behavioural signals, explains individual decisions with verifiable additive contributions, and gives an analyst a complete case workflow with an audit trail.

Test F1 is 0.75, PR-AUC 0.7629, false positive rate 0.03 %, p95 latency 1.588 ms against a 50 ms budget, and 60 of 60 automated tests pass. Where the project falls short, sections 16 and 22 say so and name the fix. That combination, measured results with disclosed boundaries, is what we would want to be judged on.
